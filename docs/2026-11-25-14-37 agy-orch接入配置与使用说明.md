# agy-orch 接入配置与使用说明

## 一、本地安装与技能发现

Antigravity 会自动扫描 `~/.gemini/config/skills/<skill-name>/SKILL.md` 与工作区 `.agents/skills/<skill-name>/SKILL.md`。按以下步骤把 `agy-orch` 接入本机环境：

- 确认 Node.js 版本为 24 以上，运行时不依赖第三方 npm 运行包；`skills/agy-orch/` 已包含自举运行层，既可从克隆仓库软链，也可单独复制 `skills/agy-orch` 目录安装。
- 若 `~/.gemini/config/skills/agy-orch` 尚未存在，在仓库根目录创建软链接指向 Skill 目录：

```bash
ln -s "$(pwd)/skills/agy-orch" ~/.gemini/config/skills/agy-orch
```

- 执行初始化命令，在 `~/.config/agy-orch/config.json` 生成默认角色配置（该命令不会修改 `~/.codex/config.toml` 或既有配置）：

```bash
node ~/.gemini/config/skills/agy-orch/scripts/agy-orch.mjs config init
```

- 核对可用后端与二进制解析路径：

```bash
node ~/.gemini/config/skills/agy-orch/scripts/agy-orch.mjs backends
```

## 二、配置模型、推理强度与自定义代理

配置加载遵循由高到低的覆盖顺序：命令行参数高于环境变量（`AGY_ORCH_BACKEND`、`AGY_ORCH_MODEL`、`AGY_ORCH_EFFORT`、`AGY_ORCH_TIMEOUT_SEC`），环境变量高于目标仓库 `.agy-orch/config.json`，项目配置高于 `~/.config/agy-orch/config.json`，最后回退到后端内置默认值。

出于安全边界考虑，目标仓库的 `.agy-orch/config.json` 只读取 `roles` 与 `defaults` 字段；任何尝试覆盖 `backends`、`binary` 或执行命令的键都会被忽略并记录在 `sources.ignored_untrusted_project_keys` 中。

### 调整模型与推理强度

默认生成的 `~/.config/agy-orch/config.json` 为 `lead`、`reviewer`、`implementer` 三个角色设置参数。若实际账号使用的 Codex 模型名称不同，可以直接修改配置文件中的 `model` 或在调用时指定 `--model`：

```json
{
  "roles": {
    "lead": {
      "agent": "agy",
      "backend": "agy",
      "model": "gemini-4"
    },
    "reviewer": {
      "backend": "codex",
      "model": "gpt-6.2-sol",
      "effort": "xhigh",
      "max_rounds": 2,
      "timeout_sec": 600
    },
    "implementer": {
      "backend": "codex",
      "model": "gpt-6.2-sol",
      "effort": "high",
      "timeout_sec": 900
    }
  },
  "defaults": {
    "timeout_sec": 900,
    "max_rounds": 2
  }
}
```

- 验证某个项目下的最终生效参数：

```bash
node ~/.gemini/config/skills/agy-orch/scripts/agy-orch.mjs config resolve --cwd /path/to/repo --role reviewer
```

- 当指定的 `--model` 或 `--effort` 被后端拒绝时，运行时会返回 `failure_kind: "invalid_parameter"` 并终止，不会自动改用其他模型顶替。

### 接入自定义代理后端

仓库已在 `skills/agy-orch/backends/` 内置 `agy.json`、`codex.json`、`qodercli.json`、`pi.json` 与 `claude-code.json`。若要启用新后端或覆盖已有后端，在 `~/.config/agy-orch/backends/<name>.json` 写入同名 JSON Profile 即可，无需改动运行时源码：

- 在新 Profile 中声明 `binary`、`output_protocol`（`codex-jsonl` / `jsonl-generic` / `json` / `text`）、`capabilities`、`exec` 参数映射以及 `resume` 规则（必须设置 `never_use_last: true`）。
- 在 `~/.config/agy-orch/config.json` 新增自定义角色（例如把 `security_reviewer` 绑定到 `claude-code` 或 `qodercli`），执行时通过 `--role security_reviewer` 或 `--backend qodercli` 切换。

## 三、端到端使用示例

以下三个场景对应日常开发中最常见的请求类型，展示 Gemini 如何决定是否调用 `agy-orch` 以及如何完成交接、裁决与失效检查。

### 示例 1：简单样式与文案调整直接跳过重流程

用户请求：把首页按钮的圆角从 4px 改成 8px，并将按钮文案从“提交”改成“保存修改”，只改 `src/styles/button.css` 和 `src/constants/labels.ts`。

- 第一步：Gemini 调用 `triage` 做轻量判断：

```bash
node "$SKILL_DIR/scripts/agy-orch.mjs" triage \
  --summary "把首页按钮圆角从 4px 改成 8px，文案从提交改成保存修改" \
  --files "src/styles/button.css,src/constants/labels.ts" \
  --kind style
```

- 分流结果：`decision` 为 `skip_heavy_flow`，`risk_level` 为 `trivial`，`recommended_commands` 为空数组。
- 后续动作：Gemini 直接修改这两个文件并自检展示效果，不调用 `review-plan`、`delegate` 或 `review-changes`，避免无谓延迟与消耗。

### 示例 2：前端重复提交与竞态缺陷审查及有界修复

用户请求：结账页连续点击提交会发出两笔请求，而且先发出的失败响应偶尔会覆盖新请求的成功提示。修好这个交互问题，并让 Codex 核查有没有残留状态竞态。

- 第一步：运行 `triage` 确认风险。摘要命中重复提交与竞态关键词，`decision` 返回 `use_agy_orch`（推荐执行 `review-changes` 或先修后审）。
- 第二步：Gemini 准备完整上下文交接包 `/tmp/checkout-packet.json`，逐字保留用户的 `original_request`、`goal`、`acceptance_criteria`、`constraints`、`non_goals` 与 `relevant_files`，并限定 `scope.allowed_paths` 为 `["src/checkout/submit.ts", "tests/checkout-submit.test.ts"]`。
- 第三步：委派 `implementer`（或由 Gemini 修改后）执行只读 `review-changes`：

```bash
node "$SKILL_DIR/scripts/agy-orch.mjs" review-changes \
  --cwd /path/to/repo \
  --task-id checkout-race-fix \
  --packet /tmp/checkout-packet.json
```

- 第四步：Codex 在只读沙箱下发现问题并返回结构化 JSON：一条 `real_defect`（校验抛错前就置位了 `inFlight` 锁导致按钮永久锁死，附带具体 `evidence`、`trigger`、`impact` 与 `minimal_fix`）以及一条 `optional_polish`（建议把按钮文案抽成独立国际化字典）。
- 第五步：Gemini 使用 `dispose` 接受 `minimal_fix` 并驳回无关的 `optional_polish`：

```bash
node "$SKILL_DIR/scripts/agy-orch.mjs" dispose \
  --task-id checkout-race-fix \
  --decisions '[{"finding_id":"F1","action":"minimal_fix","reason":"将锁置位放到校验之后并加 finally"},{"finding_id":"F2","action":"reject_overdesign","reason":"当前任务不涉及国际化改造"}]'
```

- 第六步：修复代码后，运行时检测到工作区指纹变化；执行 `check-freshness --task-id checkout-race-fix` 会显示旧审阅结论已失效（`freshness_status` 为 `stale_by_code_change`，`verdict_valid` 为 `false`）。Gemini 使用 `--task-id checkout-race-fix --resume` 发起第二轮 `review-changes` 复审确认无误后向用户交付结果。

### 示例 3：多文件后端需求评审、拒绝过度设计与隔离并发修改

用户请求：新增一次性邀请码兑换接口，需要保证并发兑换时不重复发放权益；同时另一个任务正在改同一仓库的账单导出模块，注意不要互相覆盖。

- 第一步：运行 `triage --kind concurrency` 得到 `recommended_commands: ["review-plan", "delegate", "review-changes"]`。
- 第二步：Gemini 先编写简洁方案并通过 `review-plan` 让 Codex 只读审查。若审阅意见里出现一条未列在需求中的“引入 Redis 分布式锁与独立异步重试队列”（归类为 `engineering_tradeoff`），同时指出一条真实的 SQLite 事务缺失问题（`requirement_gap`）。
- 第三步：Gemini 通过 `dispose` 对 `requirement_gap` 选 `accept`（补充事务条件更新），对 `engineering_tradeoff` 选 `reject_overdesign` 并附上理由（单机 SQLite 事务已满足原子性，不引入额外基础设施）。若第 2 轮结束时仍有 `real_defect` 或 `requirement_gap` 未解决，`dispose` 会把 `acceptance_status` 设为 `blocked`，不会在到达轮次上限时自动放行。
- 第四步：确认方案后，使用 `--worktree` 在独立 Git worktree 中运行 `delegate`，与同一主工作区正在进行的另一个任务隔离开，避开单写者锁冲突：

```bash
node "$SKILL_DIR/scripts/agy-orch.mjs" start delegate \
  --cwd /path/to/repo \
  --task-id invite-redeem \
  --packet /tmp/invite-delegate.json \
  --worktree
```

- 第五步：通过 `status --task-id invite-redeem` 查看进度。若中途因超时或执行 `cancel --run-id <id>` 中断，先查看返回里的 `execution_status`（如 `partial` 或 `cancelled`）和 `changed_files` 确认磁盘实际变更，再决定继续 `--resume` 还是清理重跑。完成后在目标分支集成改动并做一轮终态 `review-changes`。
