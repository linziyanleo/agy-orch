# 本机环境与参考项目核查

## 本机 CLI 与运行行为核实

### Codex CLI（codex-cli 0.172.0）

- 二进制路径为 `~/.local/libexec/codex-retained-runtime/entry/codex`（由 `PATH` 解析），版本输出为 codex-cli 0.172.0。
- 参数位置差异（经 codex exec --help、codex exec resume --help 与实际参数解析测试确认）
  - codex exec 支持 -C / --cd、-s / --sandbox（read-only | workspace-write | danger-full-access）、-m / --model、-c / --config、--output-schema、-o / --output-last-message、--json、--ephemeral、--worktree、--add-dir、--skip-git-repo-check。
  - codex exec resume 仅在自身子命令下接受 -c / --config、-m / --model、--output-schema、-o / --output-last-message、--json、--ephemeral、--worktree、--skip-git-repo-check、--last、--all；不接受 -C / --cd 与 -s / --sandbox。
  - 实测在 resume 之后传入 -C 或 --sandbox 会直接报错退出（error: unexpected argument '-C' found / '--sandbox' found）。
  - 实测将 -C、-s read-only、-m、-c、--skip-git-repo-check、--json 放在 resume 之前（即 codex exec [GLOBAL_OPTS] resume <SESSION_ID> <PROMPT>）可以通过 CLI 参数校验并进入 thread/resume 阶段。
  - codex exec review 支持 --uncommitted、--base、--commit、-m、-c、--output-schema、-o、--json、--ephemeral、--skip-git-repo-check、--worktree 与可选提示词，不直接接受 -C 或 -s。
- JSONL 事件流格式（经 codex exec --ephemeral --sandbox read-only --json 实测确认）
  - 会话启动首行发出 thread.started，携带 thread_id 字段。
  - 本机 ~/.codex/config.toml 开启了实验特性且未关闭提醒时，Codex 会在 turn.started 之前发出一条 item.completed 事件，其 item.type 为 error，message 为 Under-development features enabled 警告；当传入未知模型名时，也会先发出一条 item.type 为 error 的模型元数据回退警告。这两类 item.completed 警告属于非致命提示，不应被当作终止错误。
  - 随后依次出现 turn.started、一条或多条 item.completed（最终文本在 item.type 为 agent_message 的 item.text 中），正常结束时出现 turn.completed（携带 usage 字段）。
  - 实测传入不可用模型名 -m invalid-model-xyz 时，在 turn.started 之后发出顶层 type 为 error 的事件与顶层 type 为 turn.failed 的事件，不发出 turn.completed。因此 JSONL 解析应区分顶层 error / turn.failed 与 item.completed 内部的非致命警告项。
- 进程组回收行为（-pgid SIGTERM / SIGKILL）
  - 以 detached: true 启动 codex exec，其 pid 与 pgid 一致；向 -pgid 发送 SIGTERM 后，1.5 秒内进程组已完全退出。
  - 另对 detached: true 拉起的子进程树（sh 启动 sleep 30）验证，向 -pgid 发送 SIGTERM 后父子进程均退出；先 SIGTERM、等待 2 秒后补 SIGKILL 的两段式清理对独立进程组有效。

### 可扩展后端 CLI 摘要

- qodercli（`~/.local/bin/qodercli`）
  - 非交互执行使用 -p / --print，输出格式支持 -o / --output-format json（以及文本流式参数）。
  - 工作目录使用 -w / --cwd <dir>；模型使用 -m / --model；推理强度使用 --reasoning-effort <level>；思考模式使用 --thinking <auto|adaptive|enabled|disabled>。
  - 权限与工具控制使用 --permission-mode <default|accept_edits|bypass_permissions|dont_ask|auto>、--tools <tools...>（空字符串禁用全部工具，Read,Grep,Glob 可用于只读路径审阅）及 --allowed-tools <tool>。
  - 会话控制支持 --no-session-persistence、-r / --resume [id]、-c / --continue、--session-id <id>、--worktree [name]、--max-model-request-retries <count>。
  - 提示词通过命令行位置参数传递（可用 -- 分隔），超长提示词需防范宿主 ARG_MAX 限制；在非登录 shell 环境中拉起时可能需要读取登录 zsh 环境。
- pi（/opt/homebrew/bin/pi）
  - 非交互执行使用 -p / --print，输出模式使用 --mode <text|json|rpc>。
  - 模型与思考强度使用 --provider <name>、--model <pattern>（支持 provider/id 或附带 :<thinking>）、--thinking <off|minimal|low|medium|high|xhigh|max>。
  - 工具与会话控制支持 --tools <tools>（例如 read,grep,find,ls）、--exclude-tools、--no-tools / -nt、--no-session、--session <path|id>、--session-id <id>、-c / --continue、--no-extensions / -ne、--no-skills / -ns。
  - 无专用 --cwd 参数，需通过子进程 cwd 控制工作目录。
- agy（`~/.local/bin/agy`）
  - 非交互执行使用 -p / --print（别名 --prompt），输入格式 --input-format <text|stream-json>，输出格式 --output-format <text|json|stream-json>。
  - 模型与推理强度使用 --model、--effort <low|medium|high|xhigh|max>；运行模式与隔离使用 --mode <accept-edits|auto|plan>、--sandbox、--disable-slash-commands、--print-timeout、--json-schema。
  - 会话恢复使用 --conversation <id>（别名 -r / --resume）或 -c / --continue；无 --cwd 参数，需通过 spawn 的 cwd 传入工作目录。
  - stream-json 模式下，事件对象携带 conversation_id，终态通过 event 为 result 或直出 status 为 SUCCESS / ERROR 的 JSON 对象返回，包含 response、usage 与 structured_output。

### Antigravity 技能发现与本机可复用模式

- Antigravity 技能发现与 Magpie 路由机制
  - 根据内置 agy-customizations 文档与本机 ~/.gemini/config/skills/ 目录检查，Antigravity 自动扫描工作区 .agents/skills/*/SKILL.md（优先级最高，沿目录向上查找至仓库根）以及全局 ~/.gemini/config/skills/*/SKILL.md，按渐进披露仅先注入 name 与 description。
  - 本机 ~/.gemini/config/skills/ 下除了若干直接软链（grill-me、gsap、handoff、retro），还包含指向 ~/.config/magpie/skill-router/dab420bdb91d 的 magpie-skills 软链。Antigravity 启动时只把 magpie-skills 作为单个全局 Skill 识别，其余 28 个技能存放于 magpie-skills/.skills/ 下，由主代理读取 magpie-skills/SKILL.md 路由表后再按路径加载对应 SKILL.md。
- independent-review 可复用设计（~/.gemini/config/skills/magpie-skills/.skills/independent-review/）
  - 声明式后端配置：backends/*.json 定义 schema_version、kind（argv-stdin-jsonl 或 adapter-prompt-file）、discovery.binaries（支持环境变量覆盖、basename 校验与 sha256 记录）、identity（flag 或 args 模板拼写）及按模式区分的超时；用户覆盖目录为独立受控配置目录，绝不从被审阅仓库读取配置或模板，且对未知字段 fail-closed。
  - 传输态、审阅结论与本地裁决分离：result-contract.md 将 outcome（not_started / failed / unknown / success）、verdict（approve / request_changes / inconclusive）和本地处置（accepted / rejected / unverified）明确拆开。
  - 失败与重试边界：safety-and-retry.md 规定不自动重试 unknown 状态、不在超时或丢输出后静默切换后端；parse_jsonl_terminal_message 要求必须出现 turn.completed 与非空 agent_message，同时只把顶层 error / turn.failed 判为错误，不误杀 item.completed 警告。

## 三个外部参考仓库源码审计

### 1. vacuityv/codex-plugin-antigravity

- 参数传递（model / effort / sandbox）
  - model 与 sandbox 在 task 子命令下会传入 buildCodexArgs；review 子命令解析 --model 但不传 sandbox（依赖 codex exec review 默认行为）。
  - 缺陷：codex-runner.mjs 的 cmdTask 解析了 effort 标志（parseFlags(tokens, ["model", "effort", "sandbox"])），但调用 buildCodexArgs 时完全没有传递 effort，且 buildCodexArgs 也不支持 -c model_reasoning_effort；reasoning effort 被静默丢弃。
- 会话跟踪与恢复
  - 不解析或保存 Codex thread_id，仅在 task 中提供布尔开关 --resume-last，直接拼接 codex exec resume --last。
  - 缺陷：buildCodexArgs 在 args.push("resume", "--last") 之后继续追加 -C、-s、-o 与 --skip-git-repo-check。在本机 codex-cli 0.172.0 实测中，codex exec resume 不接受 -C 与 -s，因此 --resume-last 会直接因 CLI 参数非法失败；同时使用 --last 会在并发或跨终端操作时漂移。
- 取消与子进程回收
  - launchBackground 启动 detached 的 node codex-runner.mjs __run-job <id>，runJob 记录外层 Node 进程自身的 process.pid 到 meta.json，再由 runCodexToLog 启动 codex 子进程（未设 detached，也未保存 codex PID）。
  - 缺陷：cmdCancel 只调用 process.kill(meta.pid)，即只杀死外层包装脚本进程，未向 -pgid 发信号，也未等待 SIGKILL；codex CLI 及其子进程会变成孤儿继续运行。
- 文档与代码不一致
  - README.md 宣称 --resume-last 可用且仅需通过 job store 管理任务；实际代码既没有记录 sessionId，也因为参数顺序把 resume --last 写坏。
  - commands/review.md 的 argument-hint 写了 --wait，但 cmdReview 与 parseFlags 从未处理 --wait。
- 可借鉴与应规避
  - 可借鉴：结构极简、零第三方依赖的 runner 入口、不依赖私有协议直接驱动 codex exec。
  - 应规避：外层包装 PID 当作进程组终止、静默丢弃 effort、不解析 --json 事件流直接依赖退出码和原始日志、使用 --last 恢复会话。

### 2. CourageHW/agy-handoff

- 参数传递（model / effort / sandbox）
  - codex.mjs 的 buildCodexExecSpec 支持显式校验并透传 -m <model>、-c model_reasoning_effort=...、-s <read-only|workspace-write>（在 resume 分支改用 -c sandbox_mode=...，以绕开 exec resume 不接受 -s 的问题，同时不再传 -C 而依赖 spawn 的 cwd）。
  - agy.mjs 与 claude.mjs 同样对 model、effort 与 mode 做白名单校验与映射。
  - 隐患：config.mjs 中 BUILTIN_DEFAULTS 把 codex 默认模型硬编码为 gpt-6.2-sol（claude 为 claude-opus-5-5），若未覆盖配置，在当前常见 Codex 账号环境中会触发模型不支持错误；此外在未开启 --json 且未指定 outputSchema 时，buildCodexReviewSpec 的 canUseNativeReview 分支会退回原生 codex review，丢弃 jsonStream 进度与结构化输出能力。
- 会话跟踪与恢复
  - 通过 events.mjs 解析 thread.started 获取 thread_id（或从 stderr/stdout 正则兜底提取），保存到 job meta.json 的 sessionId；默认禁止在 workspace-write 模式下使用 sessionId="last"，也禁止对 --last 任务做 retryJob。
  - 仍保留了对 sessionId="last" 的部分支持（read-only 下允许），存在多会话并发时命中错误上下文的风险，但在 MCP 层和 retry 层做了较强限制。
- 取消与子进程回收
  - common.mjs 的 terminateProcessTree 在 POSIX 下调用 process.kill(-pid, signal)（配合 spawn 时 detached: true），超时与取消均有 SIGTERM 等待 2 秒再补 SIGKILL 的机制。
  - 局限与不一致：cli.mjs 明确禁止 --background（提示仅 MCP 服务支持），而 jobs.mjs 的 cancelJob 强依赖内存中的 activeChildren Map；当通过 cli.mjs 的 agy-handoff jobs cancel <id> 跨进程取消时，会因 activeChildren 为空而拒绝发信号（返回 Job is not owned by this server instance）。
- 文档与代码不一致
  - README.md 描述了较完整的多引擎协同与重试体验，但命令行入口本身不支持 --background 与跨进程 cancel；此外默认内置模型名（如 gpt-6.2-sol）与常见真实环境模型名不一致。
  - events.mjs 的 parseCodexJsonlOutput 遇到 turn.completed 时会直接把 error 重置为 null，对退出码为 0 但缺少 turn.completed 的半截流仅靠外层 exit code 判断，在部分场景可能放过不完整响应。
- 可借鉴与应规避
  - 可借鉴：context.mjs 的路径穿越与软链逃逸检查、敏感文件名过滤与大小上限控制；validateWorkspaceWriteCwd 对根目录与敏感家目录的防护；common.mjs 的进程组终止和 Windows shim 处理；反递归环境变量标记（AGY_HANDOFF_NESTED=1）与禁用自插件参数注入。
  - 应规避：在配置文件中硬编码虚构或易过期的默认模型名；把 cancel 绑定到单进程内存 Map 而无法跨 CLI 进程管理后台任务；允许 read-only 回退使用 --last。

### 3. openai/codex-plugin-cc

- 参数传递（model / effort / sandbox）
  - 通过 codex app-server 的 JSON-RPC 协议（thread/start、thread/resume、turn/start、review/start）传递 model、effort 与 sandbox（read-only / workspace-write），并将 spark 映射到 gpt-5.3-codex-spark。
  - 缺口：codex-companion.mjs 中 handleReviewCommand（review 与 adversarial-review）解析 options.model，但未解析或传递 --effort；只有 task 子命令支持 --effort。
- 会话跟踪与恢复
  - 维护按 workspace 路径哈希隔离的 state.json 与单任务 JSON 文件，并记录 Claude 会话 ID（CODEX_COMPANION_SESSION_ID）与 Codex threadId、turnId。
  - 恢复机制通过同会话最近任务记录或 thread/list 按线程名称前缀检索，不依赖 CLI 的 --last；但若在同一仓库同时并行运行多个无会话环境变量的命令行进程，findLatestResumableTaskJob 仍会取时间最新的一条。
- 取消与子进程回收
  - handleCancel 先通过 app-server 发送 turn/interrupt，再调用 terminateProcessTree(job.pid)（POSIX 下先尝试 process.kill(-pid, "SIGTERM")）。
  - 缺陷：spawnDetachedTaskWorker 使用 detached: true 启动 task-worker，可被 -pid 杀掉；但 broker-lifecycle.mjs 与 app-server.mjs 启动的 codex app-server / broker 默认复用且单独托管，如果由直接客户端连接或未及时清理，取消 task-worker 后不会自动关闭共享 broker，且 terminateProcessTree 只发送了一次 SIGTERM，没有升级 SIGKILL 兜底。
- 文档与代码不一致
  - README.md 与 commands/review.md、commands/adversarial-review.md 均说明支持 --background，并由 codex-companion.mjs 接收该标志；但实际上 codex-companion.mjs 的 handleReviewCommand 根本没有读取 options.background，始终以 runForegroundCommand 同步阻塞执行，后台执行完全依赖 Claude Code 外层的 Bash(run_in_background: true)。
- 可借鉴与应规避
  - 可借鉴：按仓库 realpath 哈希隔离状态目录；先软中断 turn 再清理进程组；schemas/review-output.schema.json 的结构化审阅输出约束；任务线程与状态预览分离。
  - 应规避：引入常驻 socket broker 与 app-server 协议复杂度（对轻量编排 CLI 而言维护成本高且跨平台易留孤儿进程）；只在文档里写后台模式却依赖宿主工具参数实现。

## 对 agy-orch 实现的直接约束与建议

- Codex 命令拼装
  - 新建会话：codex exec -C <cwd> -s <read-only|workspace-write> [-m <model>] [-c model_reasoning_effort="<effort>"] --output-schema <file> -o <file> --json [--ephemeral] [--skip-git-repo-check] -
  - 恢复会话：必须把 -C <cwd> 与 -s <sandbox> 放在 resume 子命令之前（codex exec -C <cwd> -s <sandbox> ... resume <thread_id> -），不可放在 resume 之后；禁止使用 --last。
  - 不隐式设置硬编码默认模型（如 gpt-6.2-sol），未传 --model / --effort 时保持缺省由 Codex 自身配置决定；显式传入时按参数透传，遇到顶层 error / turn.failed 明确报告 invalid_parameter 或对应错误类型。
- JSONL 与终态校验
  - 必须要求出现 turn.completed 事件且有有效输出（或通过 -o / schema 校验），仅退出码 0 不能算 completed。
  - 解析时只把顶层 type 为 error 或 turn.failed 视为错误事件，忽略 item.completed 内部 item.type 为 error 的警告条目（如本机必定出现的 Under-development features enabled）。
- 进程组与跨进程取消
  - 无论前台还是后台任务，启动外部 CLI 时均使用 detached: true，记录子进程真实 pid 与 pgid 到状态文件，cancel 命令从状态文件读取 pgid 直接跨进程向 -pgid 发送 SIGTERM，等待 2 秒确认未退出后补发 SIGKILL 并核验存活状态，不依赖同进程内存表。
- 状态与配置隔离
  - 参考 independent-review 与 codex-plugin-cc 的隔离做法：运行时状态放在 ${AGY_ORCH_STATE_DIR:-~/.local/state/agy-orch}，不写入目标 Git 仓库；后端 profile 与配置仅从 Skill 自带目录与 ~/.config/agy-orch/ 加载，绝不加载目标仓库中的可执行配置。
- 本机技能安装与测试注意
  - 本机 Antigravity 全局发现 ~/.gemini/config/skills/<name>/SKILL.md；后续安装 agy-orch 时直接链入 ~/.gemini/config/skills/agy-orch 即可被 Antigravity 原生发现，同时注意仓库自身保留独立的 skills/agy-orch/ 目录供插件或符号链接使用。
